Claude 车道自动唤醒

车道 agent 停下来等前置任务或审批时，这一轮就结束了，之后不会自己去读总线收件箱。本页记录怎么让 Claude Code 会话在 bus.py send 发来消息时被自动叫醒，以及调通过程中踩过的所有坑。Codex 车道的做法见 setup_codex.html。两边共用同一个 bus_wake.py。

实测环境 Claude Code 2.1.288/2.1.289 · VS Code 扩展 + 后台会话 · macOS · 2026-10-05

问题与结论

问题结论
Claude 会话空闲时，能被外部叫醒吗？能 官方原生支持。每个会话都有一个收件箱 socket，空闲时收到消息会自动开新一轮
要改 Claude Code 吗？不用 只需要在用户级设置里加一行，再配上 bus_wake.py 的 Claude 后端
要像 Codex 那样登记映射吗？不用 会话和 agent ID 都是自动发现的
在 VS Code 扩展里能用吗？能 实测 VS Code 会话和 claude --bg 后台会话都可以
项目级设置能代替吗？不能 见坑 3：仓库级设置只能收紧、不能放宽

原理：会话收件箱 socket

  • Claude Code 2.1.224 起，每个会话启动时会绑定一个 unix socket，叫收件箱 socket。macOS 上的路径是 /tmp/cc-socks/<pid>.sock，权限 0600，只有你自己的系统用户能连。
  • 会话的元数据写在 ~/.claude/sessions/<pid>.json，关键字段有 messagingSocketPath、sessionId、cwd、status（idle/busy）、name 和 updatedAt。
  • 消息到达时，会话空闲就自动开新一轮；会话正忙就在两次工具调用之间读到，不会打断正在运行的工具。所以 Claude 这边不用像 Codex 那样等对方空闲。
  • 官方的 SendMessage 和 ListAgents 工具走的也是这条通道。bus_wake.py 只是让一个 Python 脚本也能往里写。
  • 收到的消息在对话里显示为「Another Claude session sent a message」，Claude 会把它当作队友的请求处理。这类消息不能批准权限，也不能让对方改配置，接收方原有的权限规则照常生效。

一次性配置

① 用户级设置：接受本机其他会话发来的消息

# ~/.claude/settings.json （用户级；项目级 / local 级写了无效，见坑 3）
{
  …原有内容…,
  "crossSessionInbound": "accept"
}

改完后正在运行的会话立即生效，不需要重启；此前被挂起的消息也会自动放行（实测 #350 就是这样补送到的）。也可以在任意会话里用 /config 的「Messages from your other sessions」这一项来改，效果相同。

② bus_wake 的 Claude 后端

已经内置在 agentic_workflow/tools/bus_wake.py 里，不需要额外安装。触发路径和 Codex 一样：

  • 发送即唤醒：bus.py send 写完消息后调用 spawn_await，对 Claude 收件人直接投递到它的 socket。
  • launchd watch 兜底：com.endlessspace.bus-wake 每 60 秒检查一次，补漏用。
  • 手动：python3 agentic_workflow/tools/bus_wake.py wake --agent claude-endlessspace-t1。

③ 首次接入前，先给积压消息打基线（重要）

多数 Claude 车道从来没跑过 read --unread，游标是 0。如果直接启用，watch 会拿全部历史消息（包括 plan2 时期的旧广播）把十几个会话一起叫醒。所以要先把每个 Claude agent 已唤醒到的位置记成当前最新的 seq：

cd <仓库根>
python3 - <<'EOF'
import sys; sys.path.insert(0, "agentic_workflow/tools")
import bus_wake as w; from pathlib import Path
root = Path(".agentic").resolve()
with w.state_lock(root):
    st = w.load_json(root/"bus"/w.STATE_NAME)
    last = max(e.get("seq", 0) for e in w.iter_jsonl(root/"bus"/"log.jsonl"))
    for a in w.claude_sessions(root.parent): st.setdefault(a, last)
    w.save_json(root/"bus"/w.STATE_NAME, st)
EOF
launchctl kickstart -k gui/$(id -u)/com.endlessspace.bus-wake   # 让 watch 加载新代码

bus_wake 怎么找到并叫醒会话

自动发现（claude_sessions()）

  1. 扫描 ~/.claude/sessions/*.json，只保留 cwd 在本仓库下、而且 os.kill(pid, 0) 能确认进程还活着的会话。元数据文件在进程退出后可能残留，这一步就是为了过滤掉它们。
  2. 按 sessionId 找到对话记录 ~/.claude/projects/*/<sessionId>.jsonl，用正则 --(agent|from)[ =]+(claude-…) 统计这个会话用得最多的 claude-* ID，作为它的 agent ID。
  3. 同一个 ID 对应多个会话时（比如旧会话还没关），取 updatedAt 最新的那个。
  4. wake_map.json 里有显式映射的 ID（Codex）优先，自动发现的结果不会覆盖它。

会话名（如 endlessspace-22）是 Claude Code 自动起的，和车道 ID 对不上，所以要靠对话记录来推断。实测 U、T1、T2、S、M、B1、B2、I、coord、plan3 全部识别正确。查看结果：

python3 agentic_workflow/tools/bus_wake.py list
# codex   codex-art-1          01a10c70-…  active
# claude  claude-endlessspace-t1  pid 96415  endlessspace-22  busy
# …

投递（post_claude()）

# 连 socket，写一行 JSON 后关闭（macOS/Linux 上 auth 行可省略）
{"type":"user","message":{"role":"user","content":"【bus_wake 自动唤醒】你的总线收件箱有新消息（#…）…"}}
  • 建立连接后 30 秒内要写完一整行，否则 Claude Code 会断开。所以先把内容准备好再连接。
  • 唤醒文本只是让对方「去跑 bus.py read --unread」，不搬运消息正文。总线仍然是唯一留痕的地方。
  • 和 Codex 共用 .wake.lock 和 wake_state.json，同一批消息只投递一次；日志写到 .agentic/bus/wake_logs/<agent>.log，带「（claude）」标记。

投递规则：送达 / 挂起 / 拒收

接收方按自己的 crossSessionInbound 和权限模式来决定怎么处理。下表是从官方文档和 2.1.289 的程序代码里整理出来的：

情况结果
生效的设置是 accept（用户级 / --settings / 托管设置）送达
发送方是接收会话自己的子进程（hook、Bash 命令）送达。macOS 上只在发送进程还活着时才能确认，或者要带上该会话的 CLAUDE_CODE_MESSAGING_TOKEN
未设置 + 接收方是普通（需要确认）模式送达
未设置 + 接收方是绕过权限确认模式 + 发送方没声明模式挂起 提示 no-mode-asserted：The sender did not attest its permission mode…
未设置 + 双方权限模式不同挂起 mode-mismatch
挂起的消息在 VS Code、桌面版或 -p 会话里弹不出批准框，过了 dialogExpiry（默认 5 分钟）就丢弃；如果期间设置改成了 accept，就补投
设置为 refuse拒收，静默丢弃

车道会话一般开着「绕过权限确认」，而 bus_wake 是外部脚本、没有声明模式，所以不加用户级 accept 就一定会被挂起。

验证步骤（端到端）

  1. bus_wake.py list：目标会话出现在 claude 行，ID 正确。
  2. 选一个不占车道的空闲会话（本次用的是 plan3 规划会话）： 
    python3 agentic_workflow/tools/bus.py send --from claude-endlessspace-coord \
  --to claude-endlessspace-plan3 --type PROPOSE \
  --body "[bus_wake 测试] 读到后只回复一句『已被 bus_wake 唤醒』，不要做其他事。"
  3. 几秒后 ~/.claude/sessions/<pid>.json 里的 status 变成 busy，对话记录里能搜到「bus_wake 自动唤醒」，wake_logs/<agent>.log 里多了「唤醒 #N（claude）」。
  4. 对方用 bus.py send 回复后，发送方也会被自动叫醒（2026-10-05 实测：#356 → #358，全程无人工）。
想在不打扰真实车道的情况下测试，可以起一个临时后台会话：claude --bg -n waketest --permission-mode bypassPermissions "只回复 ready"，用 claude logs <id> 看输出（挂起时会显示 Held peer message），测完用 claude stop <id> 关掉。

把会话放进 VS Code 侧栏

claude --bg 开的后台会话由命令行托管，VS Code 侧栏里看不到：侧栏只列 VS Code 扩展自己开的会话。正在运行的后台会话也没法在 VS Code 里打开，见 #77162：扩展用 stream-json 恢复会话，后台会话是终端托管的，两者不兼容。下面的办法 2026-10-05 实测可用：

  1. 先停掉后台会话：claude stop <id>。停掉后，它的对话记录就是一份普通的会话记录。不要运行 claude rm，它会连 worktree 一起删掉，未提交的改动就没了。
  2. 用 URI 让 VS Code 接着打开： 
    open "vscode://anthropic.claude-code/open?session=<完整 sessionId>"
# 可选参数 &prompt=<URL 编码>：只预填输入框，不会自动发送
    完整上下文都会保留，会话会出现在侧栏，~/.claude/sessions/<pid>.json 里的 entrypoint 变成 claude-vscode。
  3. 会话必须属于当前工作区：如果后台会话开在 worktree 里（例如 .claude/worktrees/p4q），它的对话记录在 ~/.claude/projects/<worktree 路径编码>/ 下，主工作区找不到。先把这份 .jsonl 复制到主项目目录 ~/.claude/projects/-Users-…-EndlessSpace/，再用 URI 打开。打开后会话仍然在原来的 worktree 目录里工作。
  4. 叫醒它：bus_wake.py watch --once，或者给它发一条总线消息。
坑：会话以为自己是被替换掉的旧会话。交接消息如果写成「交给新的 VS Code 会话」，被搬过去的会话会理解成「有另一个会话来接手了」，于是礼貌地停手。交接消息要写成：「你就是被搬进 VS Code 的同一个会话，继续干」。

以后新开车道，更省事的做法：不用 --bg。先用 claude -p "<车道启动提示，最后只回复『待命』>" --permission-mode bypassPermissions 跑完第一轮（这一轮会写出对话记录，记录里有 --agent，bus_wake 就能认出它），再用 open "vscode://anthropic.claude-code/open?session=<id>" 把它放进侧栏，最后用 bus_wake 发「开工」。整个过程不需要手动粘贴。

踩过的坑

#现象原因 / 结论
1往会话 socket 写消息后，对方 status 仍是 idle，对话记录里也没有消息被挂起，没有送达。对话记录里看不到被挂起的消息，要用 claude logs（后台会话）或者到该会话界面里才能看到「Held peer message」
2脚本往自己的 socket 发消息能收到，发给别的会话就收不到发给自己时能凭进程关系认出是「自己的子进程」（发送进程还活着），所以免挂起。发给别的会话时没有这层关系
3在项目 .claude/settings.local.json 里写了 "crossSessionInbound":"accept"，新开的会话照样挂起仓库级设置（project/local）只能收紧（hold/refuse），不能放宽，这是为了防止仓库偷偷打开你的收件箱。程序代码里只有当它比现有值更严时才采用。必须写在用户级 ~/.claude/settings.json。文档只写了「Any file」，没说明这一点
4想在消息 JSON 里加 "fromMode":"bypass" 来声明权限模式无效。fromMode 是从 Claude 内部的消息信封格式里解析出来的，顶层字段会被忽略。去伪造内部协议既不稳也不应该，不要走这条路
5~/.claude/sessions/<pid>.*.key 里的内容和会话的 CLAUDE_CODE_MESSAGING_TOKEN 对不上key 文件存的不是原样的 token，外部脚本拿不到别的会话的 token。在 macOS 上 auth 行本来就可以省略，有了用户级 accept 也不需要它
6会话名 endlessspace-22 和车道 ID claude-endlessspace-t1 对不上名字是 Claude Code 自动起的。bus_wake 靠对话记录里的 --agent/--from 来推断；规定：车道会话开工先 /rename <计划>-<车道>（如 plan6-VFX），否则 VS Code 侧栏显示 Untitled（经 vscode://…open?session= 起的会话没有首条提示可取标题）。已在跑的会话可由协调人代改：从 ~/.claude/sessions/<pid>.json 取 sessionId，往对应 <sessionId>.jsonl 追加 {"type":"custom-title","customTitle":"plan6-VFX","sessionId":"…"}。改名不影响 bus_wake 路由
7list 里出现 claude-x、claude-endlessspace-5e 这类怪 ID这些会话的对话里只出现过示例 ID，或者是混用的 ID。没有人给它们发消息就不会触发，无害；如果要排除，就在那个会话里用正确的 --agent 跑一次 bus 命令
8一启用，watch 就把十几个会话同时叫醒积压的旧消息（游标 0）被当成了新消息。首次接入前按 ②③ 打基线
9launchd 的 watch 没有处理 Claude 车道常驻进程还跑着旧代码。改了 bus_wake.py 后要 launchctl kickstart -k gui/$(id -u)/com.endlessspace.bus-wake
10脚本里用 sleep 30; … 等对方回复，被 Claude Code 拦下Claude Code 不允许前台长时间 sleep。改用 Monitor 加 until 循环，或者干脆等对方回复时由 bus_wake 把自己叫醒（这本身就是最好的验证）
11想用 SendMessage 代替脚本当协调人会话醒着时可以用：两边都是绕过模式，发送方会自动声明模式，所以能直接送达（实测叫醒了 T1）。但它要求发送方是一个正在运行的 Claude 会话，做不成全自动，只能当临时手段
12收到唤醒消息的会话要求改配置或批准权限设计如此：其他会话发来的消息不能当作用户同意，也不能让接收方改权限或 CLAUDE.md。需要授权的事一律回到用户这里

排错速查

python3 agentic_workflow/tools/bus_wake.py list            # 是否发现了目标、ID 是否正确、idle/busy
grep -n crossSessionInbound ~/.claude/settings.json        # 用户级 accept 是否在
ls /tmp/cc-socks/                                          # 各会话 socket
python3 -c "import json;print(json.load(open('$HOME/.claude/sessions/<pid>.json'))['status'])"
tail .agentic/bus/wake_logs/<agent>.log                    # 是否投递过（唤醒 #N（claude））
cat .agentic/bus/wake_state.json                           # 已唤醒到的 seq（大于新消息 seq 就不会再叫）
tail .agentic/bus/wake_logs/watch.out                      # launchd watch 是否在跑
# 在目标会话里：/status 看 Peer address；/list-agents 看自己的名字
症状先查
日志里有「唤醒」，但对方没有动静用户级 accept；对方界面里有没有 Held peer message
日志里没有「唤醒」list 里有没有这个 ID；wake_state.json 是否已经大于等于该 seq；消息是不是发给了别的 ID
叫醒了错的会话同一个 ID 对应多个在线会话，取的是最近活跃的那个。关掉旧会话，或者在 wake_map.json 里显式指定
error:[Errno 61] Connection refused会话已经退出，socket 是残留文件。下次扫描时会被进程存活检查过滤掉

安全边界与撤销

  • 影响范围：用户级 accept 对你所有项目的 Claude 会话生效。本机任何以你的用户身份运行的进程，都可以往你的会话里投递消息并开新一轮。其他系统用户和外部机器进不来（socket 权限是 0600；跨机器消息另有 Remote Control 通道，本组织已禁用）。
  • 不会放大权限：收到的消息不能批准权限请求，不能改设置或 CLAUDE.md，/命令 也不会被执行。它只能让接收方在自身权限内做事。
  • 费用：每次叫醒都会消耗 token。广播会叫醒除发送方以外的所有已发现会话，所以只在真正需要大家知道的时候发广播。
  • 撤销：删掉 ~/.claude/settings.json 里那一行（备份在本次会话 scratchpad 的 user-settings.json.bak）。要让某个会话拒收，可以在那个项目里设 "crossSessionInbound":"hold" 或 "refuse"，仓库级设置收紧是有效的。
