Codex 车道自动唤醒

车道 agent 结束一轮去等前置或 ACCEPT 后就不再运行，总线收件箱里来了新消息它也不会知道。本页说明怎么让 ChatGPT App 里的 Codex 会话在收件箱来消息时被自动叫醒，而且你在 App 里能实时看到它接着干活。

工具：agentic_workflow/tools/bus_wake.py · 实测环境 codex-cli 0.160.0 / ChatGPT App 154.0 / macOS · 2026-10-05

问题：等待中的 Codex 叫不醒

ChatGPT/Codex 的会话是按轮驱动的。一轮结束后后台没有任何进程，也没有人去轮询 .agentic/bus/。别的 agent 用 bus.py send 发来的消息只是往文件里追加了一行。Claude Code 的 SendMessage 也到不了 Codex。所以过去「等 ACCEPT / 等同步点」时，只能由人去 App 里戳它一句。

官方暂时没有原生的唤醒机制，相关需求见 #46120、#32188，都还开着。本方案只用官方现有功能拼出来，不改 App。

原理：两个后端，只有一个能共享

  • App 的本地项目由 App 自带的私有 codex app-server --listen stdio:// 托管。会话一打开，它就持有写锁（~/.codex/thread-writer-locks/<id>.lock）。从外面执行 codex exec resume 或连 daemon 都会报 already has an active writer。
  • App 的 SSH 远程项目会在目标机上执行 codex app-server proxy，接到那台机器的共享 daemon（~/.codex/app-server-control/app-server-control.sock）。把目标机设成本机 codex-local，会话就放进了本机 daemon。
  • daemon 支持多客户端。bus_wake.py 作为第二个客户端对同一个会话发 thread/resume 和 turn/start，App 这边会实时出现这一轮。
  • 会话历史两边共享，都在 ~/.codex/sessions。客户端断开后，这一轮仍在 daemon 里继续跑。

一次性配置

① 本机免密 SSH 到自己

# macOS「系统设置 → 通用 → 共享 → 远程登录」需开启（nc -z localhost 22 能通即可）
cd ~/.ssh
cp authorized_keys authorized_keys.bak-$(date +%Y%m%d)
# from= 限制这条授权只对本机来源生效，外部机器拿同一把 key 登不进来
printf 'from="127.0.0.1,::1" %s\n' "$(cat id_ed25519.pub)" >> authorized_keys
cat >> config <<'EOF'

Host codex-local
  HostName localhost
  User <你的用户名>
  IdentityFile ~/.ssh/id_ed25519
  IdentitiesOnly yes
EOF
chmod 600 authorized_keys config
ssh -o StrictHostKeyChecking=accept-new codex-local 'echo ssh-ok'

② 确认共享 daemon 在跑

ssh codex-local '~/.codex/packages/standalone/current/codex app-server daemon version'
# 期望 {"status":"running", ... "socketPath":".../app-server-control.sock"}
# 没在跑：codex app-server daemon start

③ App 里添加远程项目

在 ChatGPT App 的 Codex 里添加 SSH 远程项目，主机选 codex-local，路径选仓库根目录。侧栏项目名旁出现 codex-local ● 绿点，就说明已经连上。

开车道会话

车道会话必须开在 codex-local 项目下。有两种开法，效果相同：

# 推荐：命令行开，自动命名并登记映射；会话会出现在 App 的 codex-local 项目下
python3 agentic_workflow/tools/bus_wake.py spawn --agent codex-art-1 \
  --name "负责 plan3 的 art1 车道 · daemon" --text "你是 plan3 ART1 车道（codex-art-1）……"

# 或在 App 的 codex-local 项目里手动新开会话，聊一句让它落盘，再登记：
python3 agentic_workflow/tools/bus_wake.py map --agent codex-art-1 --thread "<会话名或 UUID>"

python3 agentic_workflow/tools/bus_wake.py list   # 查看映射与 idle/active 状态
旧会话迁移：本地项目里的旧会话迁不进 daemon，只能开新会话来接手。接手前先确认旧会话已经停下（这一轮结束了，或者在 App 里关掉），否则两个会话会同时冒用同一个 agent ID 认领任务、改文件。新会话第一轮只做接班准备：读规矩、读收件箱时不加 --unread，不 claim。

唤醒的三条路径

一套设施覆盖所有 plan：总线全局只有一份，映射按 agent ID 登记，跟 plan 无关。三条路径共用 try_wake()：在同一把锁 .wake.lock 里判断、唤醒并记录已唤醒到的 seq。所以同一批消息只会叫醒一次，三条路径同时开着也不会重复。

路径触发说明
A 发送即唤醒（主）bus.py send 写完消息后自动触发收件人在映射里，就起一个脱离的 bus_wake.py await；广播则对除发送者外所有已登记的 agent 都起一个。对方 active 时每 30 秒重查一次，空闲了立刻叫醒，最多等 2 小时。发送方不用做任何事
B launchd watch（兜底）登录即启动，60 秒轮询补漏：比如 A 等超时、daemon 当时没在跑、有人没用 bus.py 而是直接改了文件。plist 在 ~/Library/LaunchAgents/com.endlessspace.bus-wake.plist
手动bus_wake.py wake --agent X --text "…"调试，或者临时下指令
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.endlessspace.bus-wake.plist   # 启用
launchctl bootout   gui/$(id -u)/com.endlessspace.bus-wake                                 # 停用
tail -f .agentic/bus/wake_logs/watch.out
macOS 隐私限制（坑 11）：仓库在 ~/Desktop 下。launchd 启动的 /usr/bin/python3 没有访问 Desktop 的权限，会报 Operation not permitted。需要在「系统设置 → 隐私与安全性 → 完全磁盘访问权限」里加上 /usr/bin/python3（也可以加 Xcode 那份 python3），然后重新 bootstrap。A 路径是在 agent 的 shell 里运行的，不受这个限制影响。
切换车道时：新会话一旦登记映射，A 和 B 就会开始叫醒它。所以要先确认旧会话已经停下，再 map；要暂停某个 agent，就 unmap。

wake_map.json、wake_state.json、wake_logs/ 都是本机私有（thread ID 只在这台机器上有效），不要提交。

Claude Code 车道

完整配置与坑见 setup_claude.html。以下是摘要。

Claude Code 本身就支持这件事。每个会话（包括 VS Code 里的）都有一个收件箱 socket /tmp/cc-socks/<pid>.sock，会话空闲时收到消息会自动开新一轮，正在忙时则在两次工具调用之间读到。这部分 bus_wake.py 已经接好，不需要登记映射：

  • 自动发现：扫描 ~/.claude/sessions/*.json，挑出进程还活着、工作目录在本仓库的会话；再到对话记录里统计 --agent/--from 用得最多的 claude-* ID，作为它的 agent ID（同一个 ID 有多个会话时取最近活跃的那个）。bus_wake.py list 可以查看。
  • 投递格式：往 socket 写一行 {"type":"user","message":{"role":"user","content":"…"}}。
  • 必要设置：用户级 ~/.claude/settings.json 里要有 "crossSessionInbound": "accept"。
坑 12：车道会话通常开着「绕过权限确认」。按默认规则，没声明权限模式的发送方发来的消息会被挂起，VS Code 又弹不出批准框，过期后就被丢掉。写在项目或 local 级设置里的 accept 不生效：仓库级设置只能收紧、不能放宽（从 2.1.289 的程序代码确认，文档没写明）。必须写在用户级设置里，而且对你所有项目的会话都生效。改完后，正在运行的会话会立即生效，此前被挂起的消息也会一并放行。

实测（2026-10-05）：协调人 bus.py send → 规划会话被自动叫醒 → 它 bus.py send 回复 → 协调人被自动叫醒并读到回复。全程无人工。第一次接入前，先把所有 Claude 车道在 wake_state.json 里记到当前最新的 seq，否则 watch 会拿积压的旧消息把十几个会话一起叫醒。

踩过的坑

#现象原因 / 结论
1codex exec resume <App 会话> 报 thread-store conflict … already has an active writerApp 本地项目的会话被 App 私有 app-server 持着写锁。exec 方案只在会话没被任何客户端打开时才能用
2codex app-server proxy 收到 initialize 后没有任何回应，脚本卡住proxy 在这个环境下不能直接拿来当 stdio JSON-RPC 用（输出了 control socket 已被占用之类的错误）。改成直连 unix socket
3往 control socket 写一行 JSON-RPC，连接立刻被关socket 走的是 WebSocket，要先做 HTTP Upgrade 握手，客户端帧还必须加掩码。bus_wake.py 里自带一个最小实现，不依赖第三方库
4连上共享 daemon 后，resume App 本地会话仍然报 active writer共享 daemon 和 App 私有 app-server 是两个进程，App 本地项目并没有连 daemon。这就是必须用 codex-local 远程项目的原因
5新建会话后马上从另一个客户端 resume，报 no rollout found会话要跑完第一轮才会写盘。spawn 会在创建后立刻发首轮
6ssh localhost 报 Permission denied自己的公钥不在 authorized_keys 里。按 ② 追加，并加 from= 限制来源
7SSH 进来后 PATH 里找不到 codex非交互 shell 不读 .zshrc。App 会用 ~/.codex/packages/standalone/current/codex，一般不受影响；如果 App 报找不到 codex，在 ~/.zshenv 里补 PATH
8唤醒的那一轮卡住不动会话在等审批或用户输入。审批请求发给了发起这一轮的客户端，也就是 bus_wake，它不会处理，只会在日志里打 ⚠。把车道会话的审批策略设成不需要人工审批，或者去 App 里处理
9（社区已知）App 的 SSH 代理有时自己另起 app-server，不连共享 daemon见 #24542。现象和坑 4 一样，报 active writer。处理办法：codex app-server daemon restart 后重连远程项目
10文档、浏览器等界面看不到不是问题。会话就在 App 里，图片、diff 照常显示，「CLI 看东西麻烦」的问题不存在

排错速查

python3 agentic_workflow/tools/bus_wake.py list                   # 映射与状态；报错说明 daemon 没连上
ls ~/.codex/thread-writer-locks/                                  # 被持锁的会话
codex app-server daemon version                                   # daemon 是否在跑、版本是否与 CLI 一致
ps aux | grep 'codex app-server'                                  # 区分 App 私有（--listen stdio://）与 daemon
tail -f .agentic/bus/wake_logs/codex-art-1.log                    # 某次唤醒的结果
