Agentic Workflow 标准

一套独立于项目的多 Agent 协作框架：把模糊的大目标，拆成可并行、可验收、且不会互相踩文件的任务网络。

v0.2（2026-10-05 增补链·车道·波次）· 运行示例：EndlessSpace 真机四域修复 · 本仓库自身即一个 git 项目

0这是什么 / 怎么用

它是「怎么组织多个 AI agent 并行干活」的标准 + 模板 + 工具 + 实例。核心命题只有一个：

并行度上限 = 独立文件链数。想让 10 个 agent 真正并行，必须先把工作切到 10 组互不相交的文件上——而不是把 10 个 agent 堆到同一个文件。

它自己是一个 git 仓库，与任何具体项目解耦。别的项目要用时，直接：

cd <你的项目>
git clone <本仓库地址> agentic_workflow
# 然后按 templates/ 填三份文件：domains.json → task-breakdown → ownership-matrix
python3 agentic_workflow/tools/check_file_ownership.py --plan PLAN.md P1-1 P2-1 P3-1 P4-7
SPEC/（本文档）

八章标准正文：域树、任务拆分、并行模型、通讯协议、岗位、Git、状态跟踪、记忆与入口。

templates/

域树 schema、任务表、所有权矩阵、证据备注、HANDOFF，以及 3 个 JSON Schema。

tools/

6 个可执行 CLI：重叠校验、注册表、文件锁、消息总线、域树校验、任务状态。纯标准库。

EndlessSpace 完整实例：16 个一级域、48 个子任务、10 条并行链、W1–W8 波次。

八章分别回答八个问题：a 项目长什么样（域树）？b 任务怎么切（子任务）？c 怎么排并行（矩阵+波次）？d agent 怎么对话？e 谁干什么（岗位）？f 代码怎么合（Git）？g 谁做完了（状态）？h 这些规矩怎么真正进 agent 的上下文（记忆与入口）。

1总览：一条流水线

关键分工：①–④ 是「想清楚」（Planner 产出计划文档），⑤–⑥ 是「算清楚」（Coordinator 用工具把计划编译成调度），⑦–⑧ 是「做出来」（Executor 干活、Reviewer 独立复核）。

a项目解读与功能域树 battle-tested

一般的项目很大很复杂，第一步是树状搜索，建立整体认知，然后把它建成一棵功能域树（1–4 级）。

树状搜索方法

  1. 找入口：主场景 / main / 路由 / 菜单，先知道「应用从哪进」。
  2. 扫目录：按 presentation/ app/ domain/ 这类分层枚举（见工具 ls -d */ 系列）。
  3. 双向核对：把产品面（用户能看到的页面/流程）与代码面（目录/模块/依赖）对照。冲突处标记为待澄清。
  4. 建域：一级域 = 一个可独立验收的大功能面；逐级下钻，最多 4 级。
  5. 落文件：给每个叶子域标注它实际涉及的文件路径（这一步直接决定后面的并行度）。
反面教训（本框架的来源之一）：第一版的功能域是「从任务清单倒推」的，不是「从项目结构盘点」的，于是漏掉了 market / spaceport / store / devtools / fleet / war / economy 等一整批域。必须先盘点、再定域。

层级与停止规则

「最多 4 级」还不够，否则永远切不完。必须给叶子定义停止规则——三条同时满足即停：

① 文件收敛

该叶子映射到 ≤ 3 个文件。

② 验收唯一

能写出唯一一条验收标准。

③ 切分无收益

再往下切不再改变文件集合（并行度不再提升）。

④ 硬顶

level = 4 强制为叶子，不许再分。

b任务解读与拆分 battle-tested

输入通常是模糊的大任务，例如「把 Swift 版一比一迁移成 Godot 版」。拆分是一条固定五步流水线：

目标  →  影响域集（树状搜索命中） →  每域列子任务  →  每任务填「改动文件」 →  生成矩阵与波次

子任务粒度三条件

  • 一个交付物（不是「优化一下」这种无边界的描述）；
  • 一条验收标准（可判定通过/不通过）；
  • 文件集最小（改动文件越少，并行度越高）。

子任务表模板（六列）

每个子任务一行，最后一列「改动文件（仓库相对路径）」是唯一数据源——它让所有权矩阵可以被脚本自动推导和校验，而不是靠人脑记住。

c并行模型：链 → 车道 → 波次 battle-tested

先分清三个概念（v0.2，2026-10-05）

链、车道、波次不是三选一，它们回答三个不同的问题，按固定顺序产生：

概念回答的问题怎么来的性质谁产出
链哪些任务不能同时做改同一文件的任务 = 一条串行链；从「改动文件」列自动算约束（客观事实，不选择）工具（--components）
车道谁来做先定 agent 数 N，把链打包进 N 条车道；一个 agent 一条车道，按顺序从头做到尾分配（唯一派工单位）Planner 写车道表，工具校验
波次什么时候做由「车道顺序 + 同步点」按最长路径推导的时间槽时间表（派生物，不手写）工具（gantt）
v0.1 的漏洞：默认「agent 数 ≥ 链数」，于是波次顺手当了派工单。第一次 EndlessSpace 17 链配 17 agent 时没暴露；第二轮 104 任务、60+ 条单任务链，W1「峰值」≈35，没人知道谁领什么；按波次抢任务还会把同一条链拆给不同 agent（P7-4 归 A、P7-5 被 B 抢到，同一文件反复交接）。缺的是第 ⑤ 与第 ⑥ 步之间的「把链装进 N 个 agent」。

修订后的四条规则

  1. 链：工具自动算。一个任务跨两条链的文件 → 两链合并为一个连通组（check_file_ownership.py --components 打印）。
  2. 车道：唯一派工单位。计划里写车道表（| 车道 | agent | 任务顺序 | 说明 |）；一条链尽量整条归一个车道。车道之间允许共享文件，但共享文件上的跨车道任务必须被同步点排出先后——实测最大连通组有 28 个任务，要求车道完全不相交只会塌成单人。
  3. 波次：降级为派生物。跨车道依赖写进同步点表（| 后（等待方） | 先（被等任务） | 原因 |），工具按单位工期最长路径推导 W1…Wn；计划里不再手写波次行。
  4. 工具：check_file_ownership.py --lanes 校验（全覆盖 / 无环 / 跨车道共享文件已排序，否则退出 1）；task_state.py claim 在任务不属于自己车道、或前置未 done 时打 ⚠；gantt 输出「车道 × 推导波次」+ 同步点状态；board 带车道列。

流程因此变成：工具算链 → 人定 N → Planner 装车道 + 写同步点 → 工具校验并推导波次 → 每个 agent 拿一条车道做到底，只在同步点等人。下文「矩阵」「波次」两节保留 v0.1 原文作为第一次实战的记录。

开车道会话（2026-10-07 plan7 教训）：Claude 车道一律用 tools/launch_claude_lanes.py --plan <计划> --lanes A,B 开——VS Code 空标签 + 向新会话 socket 投递完整首条提示，侧栏显示 <计划>-<车道>，无需用户按回车。不要用 claude -p / claude --bg 起车道：扩展 2.1.290 起侧栏过滤 sdk-cli 与 bg 会话，open?session= 静默失败，用户看不到车道；协调人 Bash 里前台批量起 claude -p 还会被杀并拖垮协调人。开完用 bus_wake.py list 核对每个车道 ID 各有独立 pid。细节与全部错误做法见 setup_claude.html §新开车道。Codex 车道照旧 bus_wake.py spawn。

为什么按「功能域」分批是错的

初版把批次轴定成「功能域」（P1=TECH、P2=SHIPYARD…），再要求「每批 ≥10 并行」。这是根本性错误：一个功能域在文件层面往往只有 1 个文件——TECH 的 12 个子任务里 10 个都改 tech_view.gd。同一文件同一时刻只能被一个 agent 写，所以同域真实并行度 ≈ 1。

四条反思：①轴选错（并行度写在了错误的轴上）；②依赖被掩盖（真正的串行资源是文件，不是功能域）；③常识倒置（跨页面并行撞车概率远低于同页面）；④单位错位（文件系统里资源的容量单位是文件）。

矩阵：按文件分组 = 串行链

把每个子任务的「改动文件」按文件归并，落在同一文件上的任务就构成一条串行链，只能顺序执行；不同文件 = 不同链 = 可并行。

域链关键文件成员
TECH例：Tpresentation/tech/tech_view.gdP1-1 → P1-3 → P1-4 → P1-5 → P1-6 → P1-8
SHIPYARD例：Spresentation/shipyard/shipyard_view.gdP2-1 → P2-2 → … → P2-7
BATTLE例：B1presentation/tactical_hud/battle_radar_view.gdP4-7（五按钮）→ P4-9（雷达本体）
BATTLEB10presentation/tactical_hud/world_feedback_layer.gdP4-2
教训：矩阵必须逐文件核对，不能凭目录名推测。初版凭目录名想象，把 presentation/tactical_hud/* 当成一条链，还把路径写成 presentation/tactical/*（该目录根本不存在）。回到真实文件核对后发现：tactical_3d_layer.gd 实际在 presentation/helios/；五按钮（SHIPS/FLEET/TECH/RETREAT/MAP）是 battle_radar_view.gd 里的 affordance，与雷达同文件；IFF 环实际画在 world_feedback_layer.gd。结果：BATTLE 的真实并行链从误判的约 4 条，修正为 10 条。

波次：每波从不同链各取 1 个

排波次的唯一规则：同一波次内，每个任务取自不同链。这样波内零文件重叠，无需合并、不会分叉。

波次并发取法

怎么提高并行度？唯一办法是把工作切到更多互相独立的文件——重构拆分、抽新文件、把热点拆薄——而不是在同一个文件上堆更多 agent。若并发太高难协调，可先压缩 W1 再逐波放开，但绝不可把同域的多个任务放进同一波。

dAgent 通讯协议 理论 / 部分验证

并行做任务时难免互相打架，而且框架是通用的，可能一个是 Claude 的 agent、一个是 Codex 的 agent。硬约束：跨厂商、跨进程 → 通讯只能是「文件总线」，不能用内存/IPC。

协调目录结构（项目内 .agentic/）

.agentic/
├── registry.json          # 谁在干什么：agent_id/model/role/task/files/status/heartbeat
├── locks/<sha1(path)>.json # 每个文件的 CAS 锁：{path, owner, task_id, acquired_ts, ttl, seq}
├── bus/log.jsonl          # 全局权威消息流（append-only，全局一份）
├── bus/inbox/<agent_id>.jsonl  # 定向收件箱（追加式）
├── plans/<name>/         # 每个计划一个文件夹：plan.json + plan.md（源文件副本）+ events.jsonl + 视图
└── index.md               # 所有计划汇总（生成物）

消息类型（11 种）

CLAIM RELEASE CONFLICT PROPOSE ACCEPT REJECT REQUEST_HELP INTERRUPT HANDOFF BLOCKED DONE

消息体：{"seq","ts","from","to","type","task_id","body","refs"}。to = "*" 表示广播（只写 bus/log.jsonl，收件人 read 时一并读到）。

协作时序

频率约定

动作时机工具
加锁（CLAM）写任何文件之前的硬闸门file_lock.py acquire
心跳每工具步 或 ≤30sagent_registry.py heartbeat

关于「打断」——必须诚实。跨厂商没有内核级抢占。只能做协作式中断：高优先级 INTERRUPT 写入对方 inbox + registry 标 interrupt_requested，规范要求对方在下一个任务边界必须处理 inbox。真正的强抢占只能由协调者（人或编排器）发信号/杀进程完成。这套协议依赖 agent 服从，属理论/部分验证，不要当成硬保证。

e岗位与能力矩阵

目前只有两个岗位：一个分配任务的（Planner），N 个执行者（Executor）。为更高效率和质量，框架直接定义 4 个岗位，并让甘特图能挂非执行节点：

岗位职责产出所需能力甘特节点
Planner 规划者树状搜索、建域树、拆任务、排波次计划文档（a–c 章产物）长上下文、结构化写作前置（不占链）
Executor 执行者实现子任务、跑 L0/L1、交证据代码 + 证据目录代码生成、工具使用、可看截图链上的实心节点
Reviewer 复核者独立复验 L2、判定 review.json复核结论视觉比对、批判性执行节点后的依赖节点
Integrator 集成者收口合并、跑全量回归、保主干线性合并提交Git 熟练、全局视野收口串行段
Coordinator 协调者跑重叠校验、仲裁锁冲突、派发调度决定工具脚本、仲裁贯穿全程
当前落地策略：先只开 Planner×1 + Executor×N。Reviewer 与 Integrator 作为扩展点写进标准与甘特图，等质量要求上来时再启用（关键点：复核必须由「另一双眼睛」做，Executor 不得自证通过）。

fGit 分支 / worktree / 合并规范 battle-tested

采用混合模型：默认单主干直推，仅「体量大且文件完全独立」的任务才开短命 worktree。

热点文件（永远串行）

主场景 main.gd/main.tscn、测试注册 test_runner.gd、验收脚本 verify.sh、parity 矩阵、本计划文档。只在收尾集成时改。

提交规范

type(scope): 描述；只 git add 具体文件；不主动 push；docs-only 提交不得夹带代码。

合并策略

优先 rebase/squash 保线性；冲突本应由文件所有权矩阵预防（不该发生）；禁 force-push。

未跟踪文件不过夜

临时脚本放 /tmp 用后删；散落分支/worktree 必须清空。

教训：规范必须先自洽，再谈执行。执行中出现 agent 大量私拉分支/worktree、子任务做完不提交——根因不在 agent，而在早期文档自相矛盾：一边说「默认单主干直推、完成即 commit」，一边又鼓励「开 worktree 并行」。两套规则打架，agent 无所适从。规则自相矛盾时，一定要先修规则。

g任务状态跟踪 battle-tested

任务拆分得再好，只要「谁做完了、做到哪一步」靠人肉记在 Markdown 里，几天之内必然漂移。病根是把三种职责塞进同一个文件：计划、状态、视图。g 章把它拆成三层，每层只有一个真源。

PLAN · 计划

手写，只描述「要做什么、改哪些文件」；禁止写任何状态标记（不打勾）。plan 退化为纯计划。

STATE · 状态

.agentic/plans/<name>/events.jsonl，append-only 事件日志，入库 git，是唯一状态真源。状态只能靠追加事件改变。

VIEWS · 视图

看板 / 甘特 / 对账报告，全部由 task_state.py 生成，视为只读产物，禁止手改。

为什么不漂移

状态只有一条写入路径（追加事件），视图重算即自洽；计划不再承载状态，也就不会出现「勾了没做 / 做了忘勾」。

验收是「灯」，不是「门」。本章刻意不给 done 设任何前置条件——不强制证据、不比较等级、不卡住任何人。理由：快速迭代 > 精准验收；漏了不算事故，重新规划、再派任务去补就好；要有灰度思想，不追求绝对准确。卡住一个 agent 的代价，远高于漏掉一次验收。

g.1 状态机（允许前跳，终态可撤销）

五个正状态线性推进，两个旁支状态可作缓冲或终态。为降低摩擦，允许前跳——从 pending 一步记 done 也合法，只要目标不倒退。终态（done/failed）不可直接离开，但可用 revoke 追加一条补偿事件回到 active（历史不删，供纠错/反证）。

命令转移含义
claim→ claimed认领任务，声明由谁做
start→ active开工（可从 pending/claimed 前跳）
submit→ verify提交待查（可选，不必须）
done→ done标记完成（无前置条件）
block / unblock↔ blocked遇阻挂起 / 解除
fail→ failed判定失败（终态）
revokedone/failed → active发现判断有误，追加补偿事件反悔（--reason）

g.2 验收是灯：done 不设前置

done 不是「过一道门」，而只是记录一次判断。工具不要求证据、不比较等级、不因缺证据而拒绝。想留痕就写可选备注（自由文本，如截图/日志路径），不写也照样能 done。

# done 无前置条件；--note 纯自由文本，写不写都行
python3 agentic_workflow/tools/task_state.py --root .agentic done P1-3 \
    --agent a1 --note "截图 out/p1-3/ · verify.sh 退 0"

# 允许前跳：从 pending 一步到位
python3 agentic_workflow/tools/task_state.py --root .agentic done P2-7 --agent a1

# 发现判断有误：追加补偿事件反悔（历史不删）
python3 agentic_workflow/tools/task_state.py --root .agentic revoke P1-3 \
    --agent a1 --reason "当时真源已变，截图作废"

g.3 三路对账 reconcile（软报告）

工具同时读三方——计划的打勾（过渡期还残留时）、事件日志、git 工作树改动，把不一致列成四类差异。这是体检报告，不是闸门：它暴露漂移供你重新规划，落后再改都行。

python3 agentic_workflow/tools/task_state.py --plan <name> reconcile
差异类含义怎么处理
计划打勾但非 done勾了却没事件（做了忘勾 / 勾了没做）补事件；过渡期后计划不再打勾
有事件但未打勾过渡期才有意义删掉手写勾即可
未登记却已改动其文件任务还没 claim，文件已被改该 agent 补 claim（唯一的流程硬要求）
工作树改动无归属改了文件但不对应任何任务补任务或确认是收尾改动

g.4 审计收口：一次把历史灌平

框架接入一个「已经跑乱」的项目时，不要重放全部历史。做法是审计跑批 + 一次性基线，此后只向前记录：

  1. 用 git 历史、HANDOFF、截图反推每个任务的真实状态，产出差异表；
  2. 用户逐条确认 → 写成基线 JSON（含 reason / source_plan / audited_at）；
  3. seed 灌进 events.jsonl 作为起点；
  4. 从计划文档删掉所有手写勾选，plan 退化为纯计划。
关键判据：「打了勾的是否真做完了」由证据决定，而不是信任勾本身——但「证据」是给人看的，不是给机器设卡的。EndlessSpace 本次审计发现 10 个勾全部为真，另 6 个做完却忘勾：漂移方向恰好是「漏记」而非「虚报」。审计只做这一次，之后靠事件日志向前累积。

g.5 实例：EndlessSpace 基线重建

71计划任务总数
12/12P0 全部完成
6做完却忘勾
0基线后未登记改动

审计把「P0 有的完成、有的没完成」这团浆糊拆清楚了：P0 共 12 个任务全部真实完成，其中 6 个从未打勾——漂移全部来自「漏记」。基线灌入后，合作方（Codex）随即用本工具自己认领了 P1-8 / P2 系列（claim→active），对账的「未登记却已改动」从 11 条自动归零。

工具只解决一半。三层真源能消除「记录漂移」，但「未登记就先改文件」是流程违规——所以 g 章唯一保留的硬要求，就是开工前先 claim。

hAgent 记忆与入口文件：让规矩真正进上下文 battle-tested

a–g 章讲的全是协作机制。但它们共享一个前提：agent 得先读到这些规矩。这一步恰恰最容易翻车——各家 agent 工具「启动即读」的入口互不重叠：你在一个文件里定好规矩，换个工具开的窗口根本读不到。

一句话结论：一个新开的窗口接到「去做 P1-3」，默认只知道「大规矩」，不知道「P1-3 是什么、现在什么状态」——因为前者在入口文件里，后者在它不会自动读的细节文档里。必须用入口文件内的「指针」把它引过去。

h.1 坑：入口分裂 + 多份真源分叉

同一套规矩，三种工具各有各的入口，写在哪一家，另外两家读不到：

工具启动自动读的入口不读什么
OpenAI CodexAGENTS.md（从 git 根到 cwd 每级拼接，上限 32 KiB）不会自动读 CLAUDE.md
Claude CodeCLAUDE.md（四级：托管 → ~/.claude/ → ./ → ./CLAUDE.local.md）不会自动读 AGENTS.md（除非 @ 导入）
Trae被设为 始终生效（alwaysApply: true）的 .trae/rules/*.md两个都不自动读
Cursor / Copilot / Gemini.cursor/rules/*.mdc / .github/copilot-instructions.md / GEMINI.md互不通用
两个反复踩到的坑：① README.md 对任何 agent 都不是指令文件，不会被自动读；② 把同一份规矩分别抄进 AGENTS.md 和 CLAUDE.md，短时间就会内容分叉——两个文件各自「看起来都对」，但 agent 读到的规矩取决于它用哪个工具。

h.2 四类「读到程度」分类学

判断一个文件「agent 会不会读、什么时候读」，只需把它归到四类之一：

类读到程度典型形态
A每次工作必读（会话启动自动注入）AGENTS.md / CLAUDE.md / alwaysApply 规则
B优先但条件命中才读技能元数据、带 globs / paths: 的路径规则、按 description 智能匹配的规则
C不自动读，靠 agent 自主或被引用Doc/**、计划文档、HANDOFF、README.md
D跨会话记忆（后台总结后下次注入）Codex Memories、Claude auto memory
读一次 vs 每次读：A 类入口基本都是会话启动读一次，同一窗口内不会因文件改动而重读（Claude 在 compact 压缩后会重读）。所以「任务状态」这类会变的信息，不要指望「写进入口文件就自动保鲜」，而要写成去读最新真源的命令（见 h.4）。

h.3 规范一：单一真源 + 一行转发

规矩只能维护一份。选一个所有工具都能被指到的文件当真源（本框架统一用 AGENTS.md，它是开放标准、25+ 工具采用），其余入口只写「转发」：

# CLAUDE.md —— 全文只有一句转发
@AGENTS.md
# .trae/rules/project.md —— 头部 frontmatter 设 alwaysApply
---
alwaysApply: true
---
本仓库所有 agent 规矩的唯一真源是 AGENTS.md。开工前先读它，再按它指引读 Doc/** 与计划文档。
为什么是一行转发而不是「两边都写」：Claude Code 支持 @path 导入（可递归，最多 4 跳），让 CLAUDE.md 直接复用 AGENTS.md；Trae 规则只要 alwaysApply: true 就是每次必读。两者都不需要复制内容——复制就是分叉的开始。

h.4 规范二：入口文件里写「指针」，而不是写「状态」

入口文件该放的是稳定原则 + 去哪找变动信息，不该放会变的状态本身。把「任务在哪、状态怎么查」写成指针（可直接抄给任何项目）：

## 任务与状态入口（开工前必做）
- 任务定义 / 要改的文件        → Doc/<批次>计划文档.md
- 任务真实状态（唯一真源）    → .agentic/plans/<name>/events.jsonl
- 查状态：python3 agentic_workflow/tools/task_state.py --root .agentic status P1-3
- 状态机 pending→claimed→active→verify→done（允许前跳）；done 无前置，留痕写可选 --note

这样无论谁开窗口、说「去做 P1-3」，agent 启动时都会读到这段指针，被逼着去查真正的定义与状态，而不是凭记忆瞎猜。

h.5 规范三：必读 / 按需 / 细节 分层摆放

把内容按「读到的必要性」分三层，只有 A 类内容允许占用入口文件的篇幅：

层放什么判断标准
入口层（A）铁律、协作规范、提交/状态规范、任务与状态指针「不读就会犯错」的，才进这一层
按需层（B）路径专属规则、技能、模板只有碰到该类文件/场景才需要
细节层（C）架构文档、计划文档、HANDOFF、状态日志可以通过指针随时查到，不必常驻上下文
入口文件还会被截断。Codex 有 project_doc_max_bytes（默认 32 KiB）上限，超长会静默截断；Claude 官方建议 CLAUDE.md < 500 行。所以入口文件要「短而关键」，长内容必须下沉到细节层。

h.6 落地清单（任何项目通用）

  1. 定真源：选一个入口居所（推荐 AGENTS.md），把全部规矩集中过去。
  2. 做转发：CLAUDE.md 写 @AGENTS.md；.trae/rules/project.md 设 alwaysApply: true 只写转发；如有 Cursor / Copilot / Gemini 再各自加一份转发。
  3. 加指针：在真源里写「任务与状态入口」节，给出定义位置、状态真源路径与查询命令。
  4. 分层：入口只留铁律 + 指针；长文档下沉，用相对路径互相链接。
  5. 验收：新开一个（此前没参与过讨论的）窗口，只发「去做 P1-3」，检查它是否主动读了真源、查了状态，且没有冒出未定义的 UI 元素或流程。

h.7 实例：EndlessSpace 的落地实拍

文件落地前落地后
AGENTS.md只装协作/截图/验收，指「细节见 CLAUDE.md」唯一真源：吸收 CLAUDE.md 全部内容 + 新增「任务与状态入口」节
CLAUDE.md约 49 行，与 AGENTS.md 内容分叉一行 @AGENTS.md
.trae/rules/project.md不存在（Trae 读不到任何项目规矩）新建，alwaysApply: true 转发
效果：此后 Codex 读 AGENTS.md、Claude 经 @ 导入同样读到它、Trae 经 alwaysApply 规则被引到它——三家用同一份规矩，改一处即三处生效。

python3 agentic_workflow/tools/bus.py      --root .agentic send --from a1 --to a2 --type CONFLICT --body "<file> 我锁了"

# 7. 状态：认领 → 开工 → 提交 → 完成（done 无前置，留痕写可选 --note）

11实例：EndlessSpace 真机四域修复

这是本框架的来源与运行示例——一个 Swift→Godot 一比一迁移工程，用户真机实测一次性报回四类问题（SHIPYARD 三栏错位 / EQUIP 三栏全空 / BATTLE 比例不一致且不开火 / TECH 图标错乱）。完整文件见 examples/endlessspace-device-parity/。

教训 1 · 并行轴选错

按「功能域」分批 → 同域并行度 ≈ 1。正确切片是跨域；文件才是资源容量的单位。

教训 2 · 规范自相矛盾

agent 私拉分支/worktree、不提交，根因是文档同时写了「单主干直推」和「开 worktree 并行」。修规则优先于修执行。

教训 3 · 矩阵必须核对真实文件

BATTLE 链数从凭目录名误判的≈4，逐文件核对后修正为 10；presentation/tactical/ 目录根本不存在。

结论

并行度上限 = 独立链数 = T1+S1+S′1+E4+B10 = 17，对应 W1 峰值。
